## 二、拦截的本质：会话信任分，不是请求频率

1688 对敏感端点 `contactinfo.htm`（联系方式页）的判定核心是**会话是否持有有效的人机信任凭证（x5sec Cookie）**，而非简单的请求频率。

Cookie 表证据（2026-08-02 09:00 后）：

| 状态 | 名下 Cookie | 产出 |
|---|---|---|
| 整夜被拦的 30 个 IP | 仅 `cna` + `isg`（匿名基础身份） | 成功 0 |
| 人工过证的 3 个 IP | `cna` + `isg` + **`x5sec`** | 成功 29 / 28 / 19 |

触发链条：

1. 全新住宅 IP + 全新匿名会话 → 信任分为零
2. warmup 后直接深链联系方式页（1688 重点保护端点）→ 弹滑块
3. 凌晨低流量时段容忍度极低：03:19–09:37 间 30 个新 IP **全部首请求即被拦**（tmd 统计 gap=1 占 59/60）
4. 引擎自动策略「休息 → 换 IP」对此无效：换 IP 解决的是单 IP 限流，而这里是**每个新会话都欠一次人机验证**；无头模式永远过不去
5. 手动过证 = 站点为「IP+会话」现场签发 x5sec → 引擎立即写回该 IP 名下 → 后续请求带信任凭证 → 恢复产出（x5sec 短时效，需偶尔复验，09:47 又弹一次，再过证即继续）

## 三、根因：多 worker 化的三个改动叠加（git 演化线）

| 提交 | 时间 | 改动 | 对拦截率的影响 |
|---|---|---|---|
| `f6ecc87` | 07-31 00:09 | 代理新 IP 用本机 `cookies_1688.json` **播种成熟身份**（cna/t/cookie2 等） | ✅ 风控眼里是"老设备换网络出口"，基础信任分高，单 worker 时代很少被拦 |
| `8f39e31` | 07-31 01:00 | 引入**多 worker 并发**（一 worker 一通道一 IP） | ⚠️ 4 个 IP 同节奏访问同一敏感端点 = 爬虫集群画像 |
| `198c30b` | 08-01 21:59 | 引擎重构，**新 IP 取消播种**（防 Cookie 重放：同一 cna 挂多 IP 并发是重放特征） | ❌ 每个新 IP 变零信任白板会话，凌晨首请求必弹滑块 |
| `198c30b`/`cb99872` | 08-01 21:59 / 22:48 | 风控状态机「休息 → relaunch 换 IP」 | ❌ 在"所有新 IP 都被拦"的场景下变成 IP 消耗正反馈：越换越拦、越拦越换，6 小时烧 34 个 IP |

**核心结论：拦截率恶化 = 「1 个成熟身份慢慢爬」被换成了「N 个白板身份并发冲」。**
取消播种的防重放判断本身正确（多 worker 下确实构成重放特征），不能简单恢复；
但单 worker 时重放问题不存在，旧行为在单 worker 下是安全的。

## 四、结构性矛盾（待解）

1. **青果 30 分钟强制轮换 IP vs x5sec 绑 IP**：信任凭证跟着 IP 走，IP 一轮换信任作废，每个新 IP 都要重新过证
2. **warmup 过证等待会超时放弃**：warmup 检测到滑块只等 10 分钟，超时照样开工 → 零信任会话白烧 IP（09:00 启动时大概率 warmup 已弹滑块，无人看到，空转 37 分钟）
3. **凌晨 03:00–09:30 对该代理池基本是不可用窗口**：同代码同池，此期间 30 个新 IP 全部被秒拦

## 六、改进方向（按优先级）

1. **过证才开工**：warmup 或首抓命中滑块时，worker 进入无限期手动过证等待（状态板明确提示），过了才认领任务 —— 有头模式下每个 IP 都能被一次过证救活
2. **全面风控熔断**：连续多轮换 IP 后所有 worker 仍首请求即被拦（gap≤2），判定时段性风控风暴，转 30~60 分钟长休眠，不再烧 IP
3. ~~`--seed-identity` 开关~~ → 已升级为**种子身份池**（2026-08-02 实现）：`.cache/seeds/` 放多份熟身份，worker 一对一独占认领，只种设备绑定 Cookie（剔除 IP 绑定的 x5sec/sgcookie/isg），指纹按种子固定；种子在多个新鲜 IP 上被秒拦时自动判定烧毁、退回白板会话
4. **错峰**：凌晨 03:00–09:30 不跑或低频跑
5. **长期**：换支持长时驻留（sticky session）的代理，让 x5sec 有效期与 IP 生命周期匹配

## 八、遗留事项

### 1. 种子里要不要保留 x5sec？（owner 倾向：保留，下次改动时尝试）

**⚠️ 2026-08-02 13:50 关键发现：x5sec 是寿命 8~15 分钟的滚动令牌，静态播种无意义。**
cookies 表证据：所有历史 x5sec 的「签发→过期」间隔均约 8~15 分钟
（如 117.67.227.57 11:47 签发 ~11:55 过期）。活跃会话里站点会随响应
滚动续期（所以过证后能连续跑几小时），但一旦会话停下或换 IP，
令牌在十几分钟内死亡。这意味着：
- 从收割文件播种 x5sec 不可行——新 IP 启动时令牌早已过期
  （浏览器对过期 Cookie 直接丢弃，种也种不进去）
- 「过证才开工」才是正解：新 IP 现场过证拿到活令牌，然后保持活跃
  让站点滚动续期；长休息（batch_rest 15min > 令牌寿命）可能正是
  活跃期偶发 re-block 的原因之一（待验证）

**现状**：种子加载与收割都会剔除 IP 绑定的安全 Cookie（`SECURITY_COOKIE_NAMES`：
x5sec/x5secdata/x5sectag/sgcookie/sg/isg）。剔除理由：x5sec 按「IP+会话」签发，
A 地签发的凭证出现在 B 地出口 = 凭证重放特征，可能是负向信号。

**保留派理由**：
- 青果 30 分钟强制轮换 IP，每个新 IP 都要重新过证拿 x5sec，是凌晨全军覆没的
  直接原因之一；如果 1688 对 x5sec 的校验实际绑的是「设备/会话」而非严格绑 IP
  （住宅用户换 IP 是常态，风控可能容忍），带上未过期的 x5sec 可能直接免滑块
- 种子身份池已保证一对一独占，不存在同一 x5sec 多 IP **并发**出现，
  只剩「顺序迁移」场景，信号强度弱很多
- 指纹已按种子固定，设备侧链路是一致的

**风险**：若 x5sec 严格绑 IP，带旧凭证访问比不带更糟（主动暴露凭证迁移）。

**实验设计（下次改动）**：
1. ~~加 `--seed-x5sec` 开关~~（已实现，2026-08-02 14:00）：偶数 worker 种子
   保留**未过期**的 x5sec/x5secdata（A 组），奇数 worker 不含（B 组对照）；
   过期的 x5sec 加载时跳过（带过期凭证比不带更可疑）
2. 播种行为落库（`ip_events` 新增 `seed` 事件：kit 名 + 是否含 x5sec），
   A/B 归因可追溯
3. 观察指标（巡检报告直接给出）：A/B 两组各自的 gap=1 比例、窗口拦截率、
   种子烧毁率
4. 判定：A 组 gap=1 比例显著更低 → 转正为默认；更高或持平 → 回滚
5. **现实约束**：受 x5sec 8~15 分钟寿命限制，A 组只有在「收割后十几分钟内
   启动」时才有活令牌可种；当前种子池全部为过期 x5sec，A 组暂等同 B 组，
   实验需配合「开跑前重新收割 + 立即启动」才有意义
